Email in the Overview

Five fine-grained, architecturally distinct ways to bring email into the CRM Overview — each built on the proven WhatsApp foundation, each with its own answer to the problem that makes email not WhatsApp: senders do not map to prospects.

Status: For decision Audience: Product owner + implementer Scope: Overview screen (CrmView = 'overview') Supersedes: the identity-thin parts of prior email drafts

The CRM already speaks one inbound channel fluently. WhatsApp arrives, gets normalized, matched to a Prospect by phone, deduped, status-tracked, surfaced in the Overview, and drafted by the Consular. Email looks like "the same again with a different transport." It is not. This document explains precisely why, lays a shared foundation, then offers five complete solutions for the Overview — so you can pick the shape before a line of transport code is written.

01Why email is not WhatsApp

The Overview was designed around a simple, load-bearing assumption that holds for WhatsApp and breaks for email:

The WhatsApp assumption

One inbound number is one counterparty, and that counterparty is (almost always) exactly one Prospect. Matching is a single key lookup: normalizeWhatsAppNumber(phone) → scan prospects.phone → matched or unmatched. Direction is unambiguous: it came from them.

Every Overview surface inherits that assumption. NextMoveHero can say "WhatsApp waiting" because a number = a lead. TriageRail can count an activity:WhatsApp bucket because the last activity's type tells the whole story. WhatsAppMessageList groups by sender and each sender row is a lead.

Email violates this assumption in five concrete ways:

Reality of emailWhat it breaks
One prospect, many addressesThe CEO writes from ceo@acme.com, replies later from j.muster@gmail.com, and her assistant chimes in from office@acme.com. A single Prospect.email field cannot hold three identities.
One address, many peopleinfo@acme.com is three humans. A match to that address tells you the company, not the person — so it cannot pick a Contact the way a phone number does.
Senders who are not prospects at allVendors, recruiters, newsletters, your own accountant, a journalist. WhatsApp inbound is almost always a lead; email inbound is mostly not. The unmatched pile is the default, not the exception.
Many parties per messageFrom + To + CC + BCC. The counterparty is not "the From" — on an outbound it is the To; on a forwarded intro it is a CC. Direction and counterparty must be derived, not read off one field.
Threads, subjects, quoting, attachmentsWhatsApp is a flat message stream. Email is a tree: subjects mutate ("Re: Re: Fwd:"), quoted history balloons each body, signatures repeat, attachments matter. Storing a raw body as Activity.notes the way WhatsApp does will flood the timeline.

The one sentence that drives this whole spec

WhatsApp matching answers "which lead is this?" with a single key. Email matching must first answer "who is this human, and do they belong to anyone we track?" — a resolution problem with four possible outcomes, only one of which is "a known prospect." Until that question has a home, every Overview surface that touches email will either lie or drown.

What already exists (and is wasted without identity)

The good news: the data model is further along than the transport. From the code audit —

  • Prospect.email exists (lib/crm-store.ts) but is never used for matching today.
  • Contact.email exists, and contacts are already 1:many per prospect with role (decision_maker, gatekeeper, assistant, …). This is the natural home for sender identity — it is the only place the model can say "this human, this address, belongs to this prospect, in this role."
  • ActivityType already includes 'E-mail In' and 'E-mail Out' with icons (mail, mail-open) wired in LeadDetail.
  • NextMoveHero already has an "Email waiting" tier (tone email) that returns empty for lack of data.
  • TriageRail already counts an activity:Email bucket.

So the surfaces are pre-drilled. What is missing is (a) transport, (b) an identity layer that turns a raw sender into a resolved counterparty, and (c) the Overview UX for the cases the phone path never had to handle. (a) is the same shape as WhatsApp. (b) and (c) are the actual design work, and where the five solutions differ.

02The sender-identity problem, in full

Before the five solutions, the layer they all sit on. Every inbound email carries an envelope; from it we must derive a counterparty identity and a link (or non-link) to the CRM. This is the email analogue of normalizeWhatsAppNumber + the prospect scan — but with branches.

2.1 — Canonicalizing an address

Phone numbers normalize to digits. Addresses need their own canonical form so that "John Muster <J.Muster@Acme.COM>", "j.muster@acme.com", and (optionally) the Gmail dot/plus variants resolve to one key.

// lib/email-identity.ts  (new — mirrors normalizeWhatsAppNumber)
export function canonicalizeAddress(raw: string): string | null {
  const m = String(raw ?? '').match(/<([^>]+)>/)        // strip display name
  let addr = (m ? m[1] : raw).trim().toLowerCase()
  if (!addr.includes('@')) return null
  let [user, domain] = addr.split('@')
  user = user.split('+')[0]                            // drop +tag
  if (domain === 'gmail.com') user = user.replace(/\./g, '') // gmail dots
  return `${user}@${domain}`
}
export function domainOf(addr: string): string { return addr.split('@')[1] ?? '' }

2.2 — The resolution cascade

Given a canonical counterparty address, walk a deterministic cascade. The first hit wins; the confidence of the match falls as we descend.

TierMatch againstOutcome & confidence
1 · Contact exactcontacts.email (canonical)Resolved → Contact → its Prospect. Highest confidence. Picks the person, not just the company.
2 · Prospect exactprospects.email (canonical)Resolved → Prospect, person unknown. Offer to also create the Contact.
3 · DomaindomainOf(addr) vs prospect website / known company domainsProbable — same company, unknown person. Suggested link, requires one click to confirm (avoids auto-linking @gmail.com — see 2.3).
4 · None—Unresolved. Goes to the sender-triage buffer. May be a new lead, a known contact under a personal address, or noise.

Domain trap

Tier 3 must exclude free-mail domains (gmail, gmx, bluewin, hotmail, icloud, …). Matching j.muster@gmail.com by domain would link every Gmail user on earth to the first prospect that happens to use Gmail. Maintain a small FREEMAIL set; for those, domain match is disabled and the address can only resolve via Tier 1/2 exact.

2.3 — The four outcomes, and what the Overview must offer for each

  1. Resolved to a Contact — behave like WhatsApp: append an E-mail In activity to the prospect, surface it. Done.
  2. Resolved to a Prospect (no contact) — append activity and offer "save j.muster@acme.com as a contact of Acme" (one click creates the Contact with role other).
  3. Probable (domain) — hold in triage with a suggestion: "Looks like Acme — link?" Confirm attaches; dismiss demotes to unresolved.
  4. Unresolved — the genuinely new case email introduces. Three actions: Create lead (prospect pre-filled from domain + signature), Link to existing (search prospects, attach as new contact), Mute sender (newsletters/vendors never ask again — written to a mute list so they never re-enter triage).

2.4 — Deriving direction & counterparty from a multi-party envelope

WhatsApp direction is given. Email direction is derived from whether our own mailbox is the sender:

// our connected mailbox(es), e.g. filippo@filomax.ch
const isOutbound = OURS.has(canonicalizeAddress(env.from))
const counterparty = isOutbound
  ? firstNonOurs(env.to.concat(env.cc))   // who we wrote TO
  : canonicalizeAddress(env.from)         // who wrote to US
const type = isOutbound ? 'E-mail Out' : 'E-mail In'

CC participants who resolve to other contacts of the same prospect are recorded as thread participants (matters most for Solution 5); CC participants who are ours are ignored; CC participants who are unknown spawn their own (low-priority) triage suggestions only if the message itself resolved.

2.5 — Threading & body hygiene

Email is a tree. Store enough to thread, store little enough to keep the timeline readable.

  • Thread key: RFC References/In-Reply-To chain → a stable thread_id; fall back to normalized subject (strip "Re:/Fwd:") + counterparty when headers are missing.
  • Body: strip quoted history and signature before writing Activity.notes (keep a pointer to the full raw .eml on disk for "show original"). One activity row = one message's new content, not the accreted quote pile.
  • Dedup: reuse the WhatsApp pattern exactly — a email_message_id column mirrors wa_message_id; appendActivity no-ops on a repeat Message-ID.

03Shared foundation — what all five solutions build on

Identity (§02) plus this transport + model layer is common to every solution. Picking a solution does not change this part; it changes only what the Overview does with it.

3.1 — Data model additions

Stay inside the event-log-first doctrine (db/events.jsonl is truth, db/crm.db is the projection). No new database; new columns and one new buffer file.

3.3 — Surfaces already half-wired (free wins)

Independent of which solution ships, these light up the moment a resolved E-mail In activity exists:

  • TriageRail activity:Email count (already filters last-activity type).

The five solutions diverge entirely on the part that has no precedent: how the Overview handles the unresolved sender, and how much of email's tree-shaped, multi-party nature it chooses to show.

04Solution 1 — The Sender Ledger

Identity-first

A standing roster of senders, resolved once, reused forever

Treat the sender as a first-class object. The Overview gains a small "Senders" surface whose only job is to keep the unresolved pile at zero. Once a human is resolved, every future email from any of their addresses flows silently to the right lead.

Center of gravity: solve the identity problem visibly and permanently, then let the existing surfaces do the rest.

The idea

Introduce an EmailIdentity projection: every canonical address ever seen, with its resolution state (contact / prospect / muted / pending). The Overview's left rail gains one bucket under the existing channel group: Senders · N, where N is the count of pending identities. Clicking it opens a focused resolution list in the middle column — the same slot WhatsAppMessageList uses today, so no new layout region.

TriageRail Middle (Sender Ledger) Right ───────────── ───────────────────────────── ──────────── Overdue 3 PENDING SENDERS · 4 Lead detail Today 5 j.muster@acme.com "Re: Angebot" (when a row This week 9 ↳ suggests Acme AG [link][new] resolves, the office@acme.com "Rechnung" prospect opens Emails 7 ◀ ↳ domain Acme [link][new][mute] here as usual) WhatsApp 2 recruiter@hays.com "Opportunity" Senders 4 ◀ ↳ no match [new][mute] news@stripe.com "Changelog" Incoming 6 ↳ no match [new] [mute]

How the sender problem is handled

Head-on, and once. Resolution is an explicit, persistent act: linking office@acme.com to the Acme prospect writes a Contact (or an email_alt on an existing contact). The ledger remembers, so the second invoice from that address never appears in triage — it lands as a timeline activity directly. Muting writes to muted.json. The pending count is a real backlog metric the owner can drive to zero.

  • Smallest new surface — one bucket, one reused list slot.
  • Makes the multi-address reality explicit and durable (email_alt).
  • Clean separation: triage is a workspace, leads stay clean.

Effort    Medium — new projection + one list component; reuses all layout.

05Solution 2 — The Unified Thread

Maximal reuse · channel-merged

Email is just another activity; the timeline already knows how

Refuse to give email its own surface. Fold it into the same per-prospect activity timeline as calls and WhatsApp. The Overview barely changes; the work is all in making one message look right next to a WhatsApp bubble and a call log.

Center of gravity: one conversation per lead, channel-agnostic. The lead is the unit, never the inbox.

The idea

There is no email inbox in the Overview. A resolved email is an Activity of type E-mail In/Out with a subject and a cleaned body, rendered inline in LeadDetail's timeline interleaved chronologically with every other touch. NextMoveHero and TriageRail already understand email as a last-activity type, so they surface "Email waiting" leads with zero new code. The unresolved pile is handled by the smallest possible mechanism: a thin reuse of the existing WaUnmatchedBanner, renamed to a generic UnmatchedBanner that shows both channels.

LeadDetail · Acme AG — timeline (channel-merged) ───────────────────────────────────────────── Today 09:14 ✉ In "Re: Angebot Webseite" — via j.muster@acme.com "Danke, sieht gut aus. Können wir Freitag…" [reply ▸] Yest 17:02 ✆ Call 12min — left voicemail Mon 11:30 ✉ Out "Angebot Webseite" (you) ✓ sent Fri 15:40 ◔ In WhatsApp "Passt das Budget?" ✓ read

How the sender problem is handled

Minimally and inline. When a sender resolves (Tier 1/2), the activity simply carries a "via address" annotation if the address differs from the prospect's primary — so a message from the assistant reads "via office@acme.com" without needing a separate identity surface. Unresolved senders sit in the shared UnmatchedBanner with the three actions from §2.3. Domain-probable matches are auto-attached only at Tier 1/2; Tier 3 stays in the banner as a suggestion. This is the lightest treatment — it accepts that messy multi-address cases are handled per-message rather than in a standing ledger.

06Solution 3 — The Triage Lane

Dedicated inbox-in-Overview

A real email workspace, parallel to the lead list

Give email the room it needs: a grouped inbox lane inside the Overview, modeled on WhatsAppMessageList but thread-aware, where resolved and unresolved live side by side and resolution is a drag/click away.

Center of gravity: email is high-volume and needs a place to process, not just a row in a timeline.

The idea

Clicking the Emails bucket swaps the middle column from LeadList to an EmailThreadList — threads grouped by counterparty, newest first, each showing resolution state inline. Resolved threads show the linked lead badge; unresolved threads show the resolve actions. It is the WhatsApp grouped-by-sender pattern, upgraded to threads and to the four-outcome resolution model.

Hätten Sie Freitag… Mon

How the sender problem is handled

As the primary workflow. The lane is where identity gets resolved, but unlike Solution 1's standing ledger, it is reading-first: you see the subject and snippet while deciding. Linking attaches the contact and (optionally) "always route this address here." Muting removes the thread and the sender. Threads collapse the tree so "Re: Re:" is one row. This is the richest day-to-day email surface of the five.

07Solution 4 — Flight-Deck Native

Decision-first · zero inbox

The Overview never shows email — it shows what to do about it

Email never gets a surface of its own. The Consular reads it, resolves it, and distills it into Flight Deck cards and Next-Move tiers. The owner sees decisions ("Reply to Acme — they said yes"), not an inbox.

Center of gravity: the Overview is a cockpit, not a mailbox. Raw email lives in the agent layer; only the next move surfaces.

The idea

Inbound email runs the §2 cascade, then — resolved or not — is handed to the Consular, which classifies (warm / ambiguous / cold), decides whether it deserves a human action, and emits a Flight Deck card (verb: REPLY/CHASE, channel: Email, tone, reason, deadline) into the deck picks file public/__crm__/deck.json. This is the cheapest surface of the five: the deck already renders an Email card as ▶ DRAFT today (FlightDeck.tsx:29/37/96), so almost no card code is new — only the candidate-feed that scores email moves. Per the read-only-Consular firewall (WP-111), the draft itself is written by a dedicated server pass; the chat agent never sends — send is a separate gated route. Resolution ambiguity is the Consular's job: it proposes the link inside the card ("Likely Acme — confirm?"), so the human resolves in the act of deciding, never in a separate triage. Newsletters and vendors are classified cold and never produce a card.

Right column · Flight Deck (email-fed) ────────────────────────────────────────────── 1 · REPLY Acme AG red · today They accepted the proposal. Send the contract. [draft ▸] · src: ✉ "Re: Angebot" 09:14 2 · CHASE Bär GmbH amber · +2d No reply in 6 days to your quote. [draft ▸] 3 · LINK? office@acme.com grey New address — likely Acme. [confirm][new][mute] queue · 5 more · cold/filtered · 23 hidden

How the sender problem is handled

Delegated to the Consular and surfaced only when it needs a human. Confident resolutions (Tier 1/2) never bother anyone. Probable (Tier 3) becomes a lightweight LINK? card. Truly unknown but hot messages become a "new lead?" card; unknown and cold are filtered (counted, hidden, auditable). The owner's triage burden is near-zero — the cost is trust in the classifier and a hidden pile that must remain auditable.

Costs / risks

08Solution 5 — The Relationship Graph

Multi-party · B2B-native

Model the whole room: who talks to whom, on every thread

Take email's many-parties-per-message reality as the feature. Surface email at the level of the relationship — the deal room — showing every participant (From/To/CC), their role, and the web of contact between the two organizations.

Center of gravity: B2B deals are multi-stakeholder. The CC list is signal, not noise. Match the existing Contact-roster + role model.

The idea

Email participants become edges in a small graph anchored on the prospect. The Overview's detail view gains a "Deal Room" mode: the prospect's contacts down one side, our side down the other, threads as connections, each annotated with who is on it. A CFO silently CC'd on the contract thread is now visible — which is exactly the intel a B2B closer wants. This is the only solution that treats cc as a relationship signal rather than discarding it.

LeadDetail · Acme AG — Deal Room ────────────────────────────────────────────── THEM THREADS US J. Muster (decision_maker) ──"Angebot"──────── Filippo office@… (assistant) ──"Rechnung"───┐ R. Vogt (cfo) CC only ┄┄"Angebot"┄┄┄┄┘ (CC'd, never wrote — surfaced as signal) ───────────────────────────────────────────── ⚠ The economic buyer (CFO) is on the proposal thread but has never replied. Loop him in?

How the sender problem is handled

Richest of all. Every address resolves to a Contact with a role (the model already has decision_maker / cfo / gatekeeper / assistant / champion …). CC participants who are new spawn "add R. Vogt as a contact?" suggestions; the graph makes the multi-address, multi-person reality the point rather than a problem to flatten. Unresolved senders still flow through the §2 cascade, but the resolution UI is contact-role-aware ("link as: champion / gatekeeper / …").

  • Uniquely B2B; the only one that reads the CC list.

LA cross-cutting layer — email as a deal vital

The five solutions are all ways to read, resolve, or act on email. One dimension sits above all of them and composes with any: email's pulse — sent / opened / replied / silent — read as a signal of where the deal stands and fed into the pipeline automatically, rather than waiting for the owner to notice. (This is the strongest idea in the sibling specs; it is a layer, not a sixth surface.)

  • Pulse drives the pipeline. Pulse transitions feed confidence_pct and can auto-flip status to 'Awaiting reply' — an existing status, not a new one.
  • Stall & cooling detection. A proposal emailed N days ago, opened but unanswered, surfaces as a named risk; a warm thread gone quiet drops confidence and prompts a Consular-drafted re-approach.
  • Lore capture. "Opened the offer 3×, never replied" writes to intel_json, so the next teardown inherits it.
  • Feeds Solution 4. A stalling deal auto-promotes to a CHASE card on the deck — the pulse layer generates, the deck displays.

Why this belongs to the identity layer, not beside it

Pulse is only legible after a sender is resolved — you cannot attribute "opened 3×, silent" to a deal until you know whose message it was. §02 is the precondition for this whole layer. It also depends on open-tracking (read pixels), a real privacy/deliverability call for v1. Add it in a later phase atop whichever surface ships — not as a sixth solution.

10Recommendation & phasing

These solutions are not mutually exclusive — they share §02–§03 entirely and differ only in the Overview layer. The honest read:

Recommendation

Ship Solution 2 (Unified Thread) first — it is the fastest path to email being usefully present, and it lights up the four pre-wired surfaces for almost free. Then layer Solution 1 (Sender Ledger) as the durable identity workbench once volume proves the per-message resolution of Solution 2 is too repetitive. Hold Solution 4 (Flight-Deck Native) and Solution 5 (Relationship Graph) as the ceiling: 4 once the Consular's email classification is trustworthy, 5 once multi-stakeholder deals are common enough to justify the graph. Solution 3 (Triage Lane) is the alternative to 1 if the team prefers reading-first processing over a standing ledger — pick one, not both.

Phasing

  1. Phase 0 — Foundation (§02–§03). canonicalizeAddress, the resolution cascade, email-inbound-dispatch, email_message_id/thread_id/meta columns, public/_email/unmatched.jsonl, freemail + mute lists. No Overview change yet; verify with the existing timeline.
  2. Phase 1 — Solution 2. Email rows in the timeline, generalized UnmatchedBanner, ComposeModal with channel switch + email-outbound. The four pre-wired surfaces go live.
  3. Phase 2 — Solution 1 or 3. Standing ledger (durable identity) or triage lane (reading-first). Decide from observed volume.
  4. Phase 3 — Solution 4. Consular EVAL-INBOUND for email → deck cards; keep the hidden/cold pile auditable.
  5. Phase 4 — Solution 5. Deal Room + CC graph + role-aware resolution, once contacts are rich enough to carry it.

Non-negotiables across all phases

(1) Event-log-first — every email mutation is an event before it is a SQLite row. (2) Freemail domains never auto-link. (3) The cold/hidden pile is always countable and openable. (4) Bodies are cleaned of quote-history before they hit Activity.notes; the raw .eml stays on disk. (5) Outbound dedup + status mirror the proven wa_message_id/wa_status machinery.
