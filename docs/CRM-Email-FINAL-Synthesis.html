02 / What I add
Two layers CD's five do not contain.

CD's P1 to P5 are all about reading, composing, and triaging email. They never ask what email tells you about a deal, and they never let email compete for attention on merit. These two layers fill that gap and sit cleanly on top of CD's core.

LAYER XEmail as a deal vital

Email is not only a message to read. Its pulse is a signal of where the deal stands, and that signal should drive the pipeline automatically, not wait for the rep to notice.

Mockup · Overview, deals at risk
OVERVIEW · DEAL PULSEEMAIL SIGNAL

offer emailed 7d ago, opened 3x, no reply · confidence falling
NUDGE

warm thread, then silent 5d
NUDGE
Bistrot · re-engaged
replied after 2 opens · confidence rising
Features
  • Pulse drives the pipeline. Sent / opened / replied / silent feeds confidence_pct and auto-flips status to Awaiting reply (an existing status, not a new one).
  • Stall detection. An emailed proposal with opens but no reply past N days surfaces with a named cause, not a vague nudge.
  • Cooling detection. A warm thread that goes quiet drops confidence and prompts a Consular-drafted re-approach.
  • Lore capture. "Opened the offer 3 times, never replied" writes to intel_json, so the next teardown turn inherits it.
  • Feeds the deck. A stalling deal can auto-promote to a Flight Deck CHASE card (see Layer Y).

Where it sits: this is not a surface, it is logic on top of CD's backbone. It reads the same E-mail In/Out activity stream and writes prospects and intel_json. It does need open-tracking, which is a real privacy and deliverability decision (see Q4).

LAYER YEmail ranked on the Flight Deck

Email does not need its own attention surface. Email moves compete on the deck the rep already reads first, ranked by ROI-per-minute next to calls and WhatsApp.

Features
  • Email feeds the ranker. Inbound and stalled emails become candidate cards scored on the same per-minute basis as every other move, written to db/flight-deck.json.
  • Channel drives the action. channel:"email" renders ▸ DRAFT (opens a Consular email draft); phone renders ▸ CALL.
  • Reuses the archetypes already registered in flight-deck.jsx: arrears for email dunning, agenda for a scheduled follow-up, tag for a quick reply.
  • Overflow stays clean. The deck holds 1 to 6; the rest sit behind the queueCount chip, so a heavy email day never breaks the deck.

Versus CD's P1: CD has the FlightDeck "gain email rows" as a notification list. Layer Y makes it a ranked decision surface, which is what the deck already is for every other channel. Small delta in code, real delta in behaviour.

04 / Appendix
Schema and the write path.

CD's Option B is right: explicit columns, because email needs a real thread_id. The two added layers need no further columns; they read the activity stream and write existing prospect fields.

// Phase 0 — explicit columns (CD Option B), email needs a thread id
ALTER TABLE activities ADD email_message_id TEXT;
ALTER TABLE activities ADD email_thread_id  TEXT;  // reply-threading + fold
ALTER TABLE activities ADD email_status     TEXT;  // sent|delivered|opened|replied
// E-mail In / E-mail Out types + subject + body already exist (crm-store.ts:100)

// outbound, mirrors wa-outbound, NOT through the read-only Consular (WP-111)
POST /api/admin/crm/activities/email-outbound
  → transport.send({ to, subject, body, in_reply_to })   // greenfield, verify engine
  → appendEvent(E-mail Out, email_thread_id, status:'sent')  // log-first [SYNC-L]

// Layer X — pulse, no new columns, writes existing prospect fields
on email_status change → recompute confidence_pct, maybe status='Awaiting reply'
on silence > N days   → intel_json.lore += "opened Nx, no reply"; promote CHASE card
05 / Decisions
Five answers unlock the build.
  1. The transport engine. Does the "Gmail MCP, 13 tools" actually exist outside the repo? If yes, point me at it and Phase 0 shrinks. If no, we build the transport first. This is the single blocker on a real estimate.
  2. Confirm the merged plan (CD's P2 ⊕ P4 ⊕ P1 core, plus my Layer Y ranking and Layer X pulse), or re-weight the phases.
  3. Auto-send. Extend the WhatsApp trust-zone auto-send to low-stakes email, or keep every email human-approved at first. Email is higher-stakes; I lean human-approved until trust is earned.
  4. Open-tracking. Layer X's "opened 3x" needs read pixels. Useful signal, but some clients and privacy norms dislike them. In or out for v1.
  5. Identity merge. Ship channels as parallel lanes first (the P2 / P4 path), or invest in contact identity-merge now so a single cross-channel thread is reachable sooner.

Answer Q1 and Q2 and CD can spec the build for Jedi Code to wire. I propose, CD specs, Code builds. The honest headline stands: CD's spec is the stronger base, mine contributes two real layers, and the transport is not the ready asset either of us should assume.
