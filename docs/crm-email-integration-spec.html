Email in the CRM Overview

Five fine-grained proposals for integrating email as a first-class channel in the lead-management overview — each grounded in the surfaces, data model, and channel machinery that already ship today.

The premise: email is not a greenfield bolt-on. WhatsApp already proves the channel pattern end-to-end (compose modal → send route → Baileys → activity row → inbound dispatch → unmatched pool → status receipts). Email re-uses that spine, swapping Baileys for the Gmail MCP. The five proposals below differ only in the overview UX layered on top of one shared backbone.

WhatsApp is the reference implementation. The whole loop is worth naming because four of the five proposals reuse it verbatim:

Today those are dead ends (mailto links, empty counts). The work is wiring a real engine behind affordances the UI is already drawn for.

01The shared email backbone all 5 build on this

Before the overview UX, one substrate. The five proposals are five front-ends to this same backend; choosing between them does not change the backbone, only what the operator sees.

1.1 — Data model reuse + 2 optional columns

The activities table already has every field email needs (crm-store.ts:113-129): type, subject, notes (body), media_path/media_mime (attachments), wa_message_id + wa_status (id + delivery). Two cleanliness options:

OptionShapeTrade
A · discriminated reusetype='E-mail Out' ⇒ wa_message_id = Gmail msg id, wa_status = email status. No migration.Zero schema change; the wa_* names lie a little.
B · explicit columnsALTER TABLE activities ADD email_message_id TEXT; ADD email_thread_id TEXT; ADD email_status TEXT;Honest names + a thread_id we genuinely need for reply-threading. Recommended.

One field email needs that WhatsApp didn't: email_thread_id — the Gmail thread, so replies stay in-thread and the dashboard can collapse a back-and-forth into one conversation. That alone argues for Option B.

1.2 — Outbound new route

// POST /api/admin/crm/activities/email-outbound  (mirrors wa-outbound/route.ts)
{ prospect_id, to?, cc?, bcc?, subject, body, in_reply_to?, attachments? }
  → resolve recipient: to ?? contact.email ?? prospect.email
  → Gmail MCP: create_draft({to,subject,body,…}) then send  // + thread via in_reply_to
  → appendActivity({ type:'E-mail Out', subject, notes:body,
                     email_message_id, email_thread_id, email_status:'sent' })
  → { ok, activity_id, email_message_id, email_thread_id }   // 502 if MCP down

1.3 — Inbound new dispatcher

Mirror wa-inbound-dispatch: a Gmail watch (Pub/Sub push) or a 60-second poll on a labeled mailbox. For each new message: get_thread() → extract from/subject/body/attachments → match from against prospect.email then contact.email.

  • Match → appendActivity({type:'E-mail In', subject, notes, email_thread_id, media_*}); emit the activities bus event the overview already polls (15s).
  • No match → email-unmatched pool (db/email-unmatched.jsonl), exactly like WA's media/unmatched/<phone>/. When a Contact/Prospect with that address is later created, promoteUnmatchedForEmail() rescues the buffered thread — the direct parallel to promoteUnmatchedForPhone().

1.4 — EmailComposeModal parallels WaComposeModal

One component, reused by every proposal that composes inline (P2–P5). It is WaComposeModal with three additions: a Subject field, optional Cc/Bcc row, and a thread-aware header ("Reply · re: …" when in_reply_to is set). The amber channel tone (--email #e8861a) replaces WhatsApp green. "Ask AI" hits the same /consular/ask route, now returning {subject, body} instead of body-only.

Boundary — Consular stays read-only (consular/chat performs no mutations, WP-111). Sending always goes through the dedicated email-outbound route, never the chat agent's tool surface — same firewall WhatsApp respects.

02Proposal 1 — Consular-as-Inbox effort: S

AGENT-MEDIATEDzero new pane · ships first

Email lives entirely inside the right-rail chat you already have. You never open an email client — you ask. "Draft a reply to the Falcamel inquiry", "what did Silke email about the build?", "send it." Consular reads the thread (Gmail MCP search_threads/get_thread), drafts, and on your OK fires email-outbound; the result lands as an E-mail Out activity on the lead and a draft card in chat.

Features (fine-grained)

  • Read in context. Consular gains 3 Gmail tools (search_threads, get_thread, list_drafts) plus the existing SQL read path, so it can answer "summarise the last email from this lead" by joining prospect.email → thread.
  • Draft card. When Consular drafts, it returns a typed card on the same channel tc_discovery uses today (consular/chat/route.ts:98 already passes card through). New card kind email_draft: subject + body + recipient + Approve / Edit / Send buttons.
  • Send is gated. "Send" on the card POSTs email-outbound — the agent proposes, the human commits. No autonomous sending.
  • Inbound nudges. The FlightDeck push-queue (page.tsx:552, db/flight-deck.json) gains email rows: "Silke replied · 2h ago · re: build" → click scrolls the lead.

Edge cases & tradeoffs

  • Strength: least UI built, leans on the chat metaphor Consular already owns, conversational triage ("who's owed a reply?") is genuinely better than a list.
  • Weakness: no visual inbox — you can't browse mail, only query it. Power users who live in threads will feel blind. Long threads are summarised, not shown verbatim, unless you ask.
  • Doctrine risk: Consular is read-only by design; the send card must route around the agent (direct email-outbound POST from the card click), or you breach the WP-111 firewall.

Features (fine-grained)

  • Blended feed. FeedRow already maps E-mail Out→mail, E-mail In→mail-open (LeadDetail.tsx:116-131). Email rows show subject in bold + a body snippet; the existing WaMediaBlock (:1544) renders attachments (it already handles images/audio/video/docs).

  • Channel-lit icons stay truthful. The LeadList row email icon (LeadList.tsx:202) already lights "active/recent" off email activity — now it lights for real, beside the WhatsApp and Call lamps.
  • "Awaiting reply" status. An unanswered E-mail In can auto-flip the lead's status chip to Awaiting reply (one of the 5 header statuses, :729).

  • Weakness: entirely lead-centric — there is no cross-lead inbox. Anything that isn't matched to a prospect (cold inbound, a forward) has nowhere to land except the unmatched pool, which has no UI here.
  • Risk: email is verbose; without disciplined thread-folding and snippet truncation, the feed loses its scannability. The fold logic is load-bearing, not polish.

Features (fine-grained)

  • Reading pane keyed to selectedProspect.email_thread_id via get_thread() — full message bodies, quoted history, attachment chips. This is the only proposal besides P5 that shows verbatim threads.

05Proposal 4 — Triage Inbox (rail-driven) effort: S–M

EMAIL AS A SIGNALthe Emails bento becomes a real triage queue · most on-brand

Email drives what to do next, not a reading client. The TriageRail's existing Emails bento (TriageRail.tsx:128) splits into action buckets — Awaiting reply (4), Hot inbound (2), Unread — and each routes you to the relevant lead, where you read/reply in the center column (reusing P2's feed + composer). Email becomes a first-class citizen of the triage-first design the CRM is built around.

  • Weakness: you can't browse raw mail — only prospect-matched signals. "Hot inbound" depends entirely on matching; unmatched cold mail is invisible. It's a router, not a client (which is the point, but also the ceiling).
  • Risk: "awaiting reply" detection needs solid thread state — mis-firing the count erodes trust in the rail, which is the CRM's most-trusted surface.

06Proposal 5 — Dedicated Inbox View (4th tab) effort: L

FULL CLIENTa real two-pane inbox · turns strangers into leads

Add inbox beside overview · kanban · scout (page.tsx:55, 430) — a genuine two-pane email client (thread list + reading pane) that auto-matches senders to prospects and offers Attach to lead / Promote to lead. It is the only proposal that handles raw inbound volume and manufactures new leads from cold mail — the email analogue of the Scout pool.

Features (fine-grained)

  • Thread list (left) with sender, subject, time, and a match chip: "→ Lead #P011", "→ unknown". Filterable by label (Gmail list_labels/label_thread) and by matched/unmatched.
  • Reading pane (right) — verbatim thread via get_thread(), full bodies, attachments, reply/forward.
  • Lead manufacturing. "Promote → new lead" runs the same path as Scout's raw-prospects promotion (raw-prospects/[id]): seed a prospect from the sender's name/email/domain, attach the thread as the first E-mail In, drop into the overview. "Attach to lead" links an unmatched thread to an existing prospect and back-fills the activity.
  • Bulk triage: select N threads → label / archive / "create leads from all".
  • Cross-view links: a matched thread row deep-links to /crm?view=overview with that lead selected — inbox and overview are two doors to one dataset.

Edge cases & tradeoffs

  • Strength: the only option that handles cold inbound and converts strangers into pipeline; a complete email surface; the natural twin of the existing Scout pool.
  • Weakness: a separate mode — a context switch away from the lead-centric overview, and the most to build (full client + match UI + bulk ops). Risks re-creating Gmail inside the CRM.
  • Risk: scope creep into a mail client. Mitigate by scoping v1 to one label (e.g. "Leads") and matched-vs-unmatched only — not a general inbox.

08Recommendation & phased rollout

These are not mutually exclusive — they layer. The right answer is a phased blend, not a single pick: build the backbone once, then add surfaces in increasing ambition, stopping wherever the volume justifies.

PhaseShipWhy
0 · Backbone required§1 — email-outbound, inbound dispatch, status, EmailComposeModal, schema Option BEvery surface needs it; nothing user-visible decided yet.
1 · P2 + P4 recommended coreEmail lane in the Activities feed + channel-toggle composer (P2), entered via the triage Awaiting-reply / Hot-inbound bentos (P4)The two most on-brand, lowest-net-new-UI options compose perfectly: P4 is the entry, P2 is the workspace. Delivers read + reply + "who's owed a response" with almost no new frame.
2 · P1 optionalConsular gains Gmail read tools + draft cardsCheap add-on once the backbone exists; turns the advisor into a drafting partner.
3 · P5 only if neededDedicated Inbox view, scoped to one labelReach for this only when meaningful cold inbound arrives that isn't yet a lead. Until then it's a Gmail clone you don't need.
The call — Build the backbone, then P2 ⊕ P4. It is the most coherent with the WhatsApp/triage model already shipping, the least net-new UI, and it makes the dead affordances (the Emails bento, the mailto icons, the E-mail activity types) finally real. Add P1 as a low-cost multiplier. Defer P3 and P5 until inbound volume — especially unmatched volume — actually demands a reading client.
