Final specification · supersedes both proposal drafts

Email belongs in the Overview. Here is the shape, and why.

The CRM already runs WhatsApp end to end and already ranks the next move on a Flight Deck. Email is the missing second channel. Two drafts proposed how to bring it in; this is the reconciled final — the stronger ideas from each, corrected against what the code actually does, with one decision foregrounded and a build small enough to ship in phases.

How this final
was built

From draft A (the conceptual draft): the organizing axis — five proposals defined by what email is (a conversation, an inbox, a draft pile, a ranked move, a vital sign) — plus the two ideas neither I nor anyone else should drop: Flight-Deck-Native and Deal-Health Signal, and the surface/engine split in the recommendation.

From draft B (the grounded draft): hard file:line citations, the concrete send/inbound backbone, the EmailComposeModal, and the read-only-Consular firewall that the auto-draft engine must respect.

From the code itself (the correction): the deck already carries a channel:'Email' field that already renders ▸ DRAFT — so the recommended surface is nearly free. The six deck shapes are hero·dial·ticket·chevron·gauge·tag, not what A guessed. And Consular's chat is read-only (WP-111), so the engine writes around it.

01 / Foundation
What all five share, settled once.

1 · The schema already speaks email; the transport does not. activities carries E-mail In/Out with subject, notes (body), media_* (attachments) and message-id/status columns. The missing piece is transport — and it is a real decision, not a detail: a relationship-selling rep's mail must leave from his own inbox and identity, not a crm@ sending domain, or the warmth that makes the sale evaporates. The leading transport is therefore Gmail two-way (the MCP connector, or the Gmail API under it). The five proposals are about shape in the Overview; any of them runs on this transport.

2 · One discriminator, the rest is composition. Email and WhatsApp differ in cadence — email is slower, longer, threaded, often to a named role — but they are the same primitive: a message, on a channel, to a contact, about a deal. A single channel column on activities (default 'whatsapp') makes the feed and the rail queryable per channel. Email also needs one thing WhatsApp didn't — email_thread_id — so replies stay in-thread and a back-and-forth collapses to one conversation. Whether channel is surfaced as one merged stream or two parallel lanes is precisely what separates the proposals.

3 · The outbound + inbound backbone is the WhatsApp pattern, run twice. A new route POST /api/admin/crm/activities/email-outbound mirrors wa-outbound: resolve recipient (to ?? contact.email ?? prospect.email) → Gmail send → appendActivity({type:'E-mail Out', subject, notes:body, email_thread_id, status:'sent'}). Inbound mirrors the Baileys dispatcher: a Gmail watch matches from against prospect.email then contact.email → E-mail In activity, or an email-unmatched pool rescued later by promoteUnmatchedForEmail() — the exact twin of today's promoteUnmatchedForPhone(). EmailComposeModal is WaComposeModal + a subject field + cc/bcc + thread mode.

4 · The Consular is the multiplier — but read-only. The reason to pull email into the CRM is that Consular knows the deal, the contact's role, and Filippo's voice, so it can draft the reply. Every proposal leans on that. But the chat agent mutates nothing (WP-111). So "drafting" is a dedicated server pass that writes a draft to the outbox / deck.json — never the chat agent calling a send tool. The firewall that protects WhatsApp protects email identically.

Where the five genuinely diverge is the organizing idea: is email an inbox, a triage queue, a draft pile, a ranked card, or a deal-health signal? That choice cascades through the whole Overview. That is the decision in front of you.

PROPOSAL AOne Threademail is · a conversation

Email is not a new screen. It is a new bubble in the conversation you already have. WhatsApp and email merge into one per-lead thread, and the Overview stops caring which channel a message arrived on.

The core idea

A lead has one conversation; each message is tagged with the channel it travelled on. The unmatched WhatsApp bucket generalises to unmatched inbound, holding both channels. The lead detail's activity feed (already a chronological timeline, already rendering E-mail In→mail / E-mail Out→mail-open icons at LeadDetail.tsx:116) becomes the single stream — amber rows for email, green for WhatsApp. The rep stops thinking in inboxes and starts thinking in relationships, which is how a good salesperson already thinks.

PROPOSAL BThe Triage Laneemail is · an inbox

Email has its own rhythm — slower, longer, to a named decision-maker. Do not merge it, give it lanes. Dedicated Overview buckets and a triage-first workflow beside the existing ones.

The core idea

Where A blends, B separates on purpose. The TriageRail's existing Emails bento (TriageRail.tsx:128, the amber data-tone="email" tile that today just counts) splits into four action buckets, reusing the exact .fp-triage num·label·sub·arrow anatomy (:183). The honesty argument: an email is a letter, often to a gatekeeper who took days; a WhatsApp ping is a tap. Flattening them, as A does, erases a real difference. B keeps it and turns it into a clean rhythm — open the Overview, clear the email lane, clear the WhatsApp lane, move on.

  • Four email buckets: Unmatched · Awaiting-reply · Drafted-ready · Gone-quiet. Each is a queue with bulk actions; clicking one filters the LeadList and auto-opens the top lead with the composer focused on Email.

PROPOSAL CConsular Co-Pilotemail is · a draft pile

The point of email-in-CRM is not an inbox. It is that the replies are already written when you arrive. The Overview leads with a queue of Consular-drafted answers, not raw mail.

The core idea

A and B still ask the rep to read and decide. C inverts the work. Every inbound email triggers a Consular draft — voice-matched, aware of intel_json and the contact's role. By the time Filippo opens the Overview the headline is not "12 emails," it is "12 in, 9 already answered for you, 3 need a human." Raw, undrafted email is the exception the system flags, not the default the rep wades through. This is the proposal most aligned with why the Consular exists: volume that outgrew one human, handled in his voice.

The firewall correction (from the code): Consular's chat is read-only. So C's drafting is not the chat agent sending — it is a dedicated server pass (the same consular/ask path the WhatsApp modal already uses, WaComposeModal.tsx:144) that writes a draft into a review queue. The human approves; the approved row calls email-outbound. The agent proposes; the human commits. Autonomy is a dial set in Q3, not a default.

PROPOSAL DFlight Deck Nativeemail is · a ranked move

Email does not need a surface of its own. Email actions become Flight Deck cards, ranked by ROI-per-minute beside calls and WhatsApp. Email earns attention on merit or it waits — and the deck is already built for it.

The core idea — and the code already agrees

The Flight Deck already answers "what should I do right now" with 1–6 ranked picks the Consular writes to deck.json. D says email is just more input to that ranker, not a parallel world. Here is the finding that makes D the cheapest real surface: the deck is already email-aware. FlightDeckAction.channel already enumerates "Email" (FlightDeck.tsx:37), and execVerb() already renders ▸ DRAFT for any non-phone channel (:96). A hot email — "can we sign this week" — is a higher ROI-per-minute move than a cold WhatsApp nudge, so Consular pushes it as {verb:'REPLY', channel:'Email', tone:'red'} and it renders today, no new card code. A proposal emailed 7 days ago, silent, is a CHASE card. Zero new surface; the rep reads the deck first anyway.

PROPOSAL EDeal-Health Signalemail is · a vital sign

Email matters only as evidence of where a deal stands. Don't build an inbox, build deal-health detection. The Overview surfaces deals whose email state is a risk, not a list of messages.

The core idea

The most radical reframe: a rep doesn't want a mail client, he wants to know which deals are slipping. So email is consumed for signal and discarded as a surface. "Proposal emailed 7 days ago, opened twice, no reply" is a stalling deal; "champion went warm then silent" is a cooling one. Those become entries in a risk panel that drive confidence_pct and next_action automatically, and write the cause into intel_json as lore. Reading and writing full threads can still happen in Gmail; the CRM watches the pulse and tells the rep where to push. This is less a v1 surface than a layer that deepens every other proposal over time.

  • Email state as a deal vital. sent / opened / replied / silent feeds confidence_pct and flips status to "Awaiting reply" automatically.
  • Stall detection. An emailed proposal with opens but no reply past N days surfaces as a named risk; a cooling warm thread drops confidence and prompts a Consular-drafted nudge.

  • Promotes to the deck. A stalling deal becomes a CHASE card (the D surface) automatically — E generates, D displays.
  • No inbox to maintain. The CRM stays a pipeline instrument, never a mail client.

08 / The call
Recommendation.
The synthesis — sharpened by the code
Ship D as the surface (it is nearly built) and C as the engine (governed, human-gated), on the channel-tagged activities model. Hold B as overflow; fold E in over time; reach A last.

Both drafts converged on "D surface + C engine, B in reserve" — and the code makes that synthesis stronger than either argued. D (Flight Deck Native) is the right surface because it is faithful to the prioritisation philosophy already in the product and the card already renders email: channel:'Email' → ▸ DRAFT ships today (FlightDeck.tsx:96). No new screen, the smallest build of the five. C (Consular Co-Pilot) is the right engine beneath it — a REPLY card should open a draft that is already written — with the firewall correction: drafting is a server pass into a review queue, the chat agent never sends (WP-111). The human approves; email-outbound ships it.

Hold B (Triage Lane) in reserve as the overflow for days when volume exceeds a 1–6 deck; it reuses the same bento + eval machinery, so it is cheap to add later and need not ship first. Fold E (Deal Signal) in continuously — it generates the CHASE cards D displays and writes the lore C drafts from, so it compounds rather than competes. A (One Thread) is the eventual destination once identity-merge is trustworthy; its data risk means it leads nothing.

PHASE 1Transport
Gmail two-way (his real inbox, his identity). Add channel + email_thread_id to activities (event-first). Inbound matched by from-address → E-mail In or the email-unmatched pool. Build email-outbound + EmailComposeModal. No new surface yet — the feed (A's substrate) just goes bi-channel.
PHASE 2Engine — C
Inbound fires a Consular draft pass (reusing consular/ask), role-aware, proofread-gated, into a review queue. Human-approved by default (Q3). The chat firewall stays intact.
PHASE 3Surface — D
Consular pushes email actions to deck.json as REPLY/CHASE/SEND cards. The card already renders; build only the candidate-feed + the onExecute→draft wiring. This is the phase that costs the least and shows the most.
PHASE 4B + E
Add the email triage lane for high-volume days; begin folding open/reply signals into confidence_pct and intel_json, auto-promoting stalls to CHASE cards.
09 / Appendix
Data model & the build delta.

The point of the appendix: the build is small. The schema already speaks email; this adds a discriminator, a thread id, a transport, and two routes that mirror WhatsApp.

// activities — already declares E-mail In/Out (crm-store.ts:94). Add:
ALTER TABLE activities ADD COLUMN channel         TEXT DEFAULT 'whatsapp';  // 'whatsapp'|'email'|'call'|'note'
ALTER TABLE activities ADD COLUMN email_thread_id TEXT DEFAULT '';        // Gmail thread — reply threading + feed fold
// subject, notes(body), media_path/mime, message-id, status columns already exist → reused.

// outbound — new route, mirrors activities/wa-outbound/route.ts
POST /api/admin/crm/activities/email-outbound
  { prospect_id, to?, cc?, bcc?, subject, body, in_reply_to?, attachments? }
  → recipient = to ?? contact.email ?? prospect.email
  → Gmail send (create_draft → send), threaded via in_reply_to
  → appendActivity({ type:'E-mail Out', channel:'email', subject, notes:body, email_thread_id, status:'sent' })
  → { ok, activity_id, email_thread_id }              // 502 if Gmail transport down — fall back to compose-in-Gmail link

// inbound — new dispatcher, mirrors the Baileys wa-inbound path
Gmail watch/poll → get_thread → match from-address: prospect.email then contact.email
  match   → appendEvent(E-mail In)  // emits the activities bus event the Overview already polls (15s)
  no match→ email-unmatched pool  // promoteUnmatchedForEmail() on later contact creation — twin of promoteUnmatchedForPhone()

// log-first, then SQLite projection. Same [SYNC-L] invariant as WhatsApp. No JSON side-store.

Identity matching — the cost centre for Proposal A — lives in contacts: a contact's email joins phone as a key; inbound tries email, then sender-domain, then the unmatched pool, exactly as unmatched WhatsApp works today. Nothing here is a new subsystem. It is the WhatsApp pattern, run a second time, on a second transport, surfaced — for the recommended path — through a deck card that already renders.
